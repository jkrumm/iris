## 1. MCP-based Xcode control

### XcodeBuildMCP → MobileBuildMCP (renamed, not forked)

Both legacy slugs — `cameroncooke/XcodeBuildMCP` and `getsentry/XcodeBuildMCP` — resolve to **`getsentry/MobileBuildMCP`** via the GitHub API, i.e. a rename: MIT, 6,511 stars, created 2025-03-09, last push 2026-10-27, not archived. npm shows the split cleanly: `mobilebuildmcp` is at **2.7.1** (published 2026-09-23, repo `getsentry/MobileBuildMCP`), while the legacy `xcodebuildmcp` package is pinned at **2.7.0** (2026-07-23) and has not been deprecated. `xcodebuildmcp.com` is still the docs host but now serves MobileBuildMCP branding.

**Requirements (README verbatim):** "macOS 14.5 or later; Xcode 16.x or later; Node.js 18.x or later (not required for Homebrew installation)." Xcode 26/27 is not in the README requirements; Xcode 26.3+ appears only in the *clients* doc for in-IDE agents, and v2.7.1 release notes (search snippet only) mention Xcode 27 simulator support through Device Hub.

**Install for Claude Code** (documented, verbatim): `claude mcp add MobileBuildMCP -- npx -y mobilebuildmcp@latest mcp`; Homebrew route `brew tap getsentry/xcodebuildmcp` + `brew install mobilebuildmcp`. For agents *inside* Xcode the docs require "Xcode 26.3 or later with the Claude Code agent installed under Xcode Settings → Intelligence → Anthropic" and configure MCP in `~/Library/Developer/Xcode/CodingAssistant/ClaudeAgentConfig/.claude.json`.

**Tools mapped to your list:** build/run-on-simulator → `build_sim`, `build_run_sim` ("builds the scheme, installs the .app on a booted simulator, and launches it, with logs captured to a file"), `clean`, `list_schemes`, `list_sims`, `boot_sim`; device install → `build_device`, `install_app_device`, `launch_app_device`; macOS → `build_macos`/`build_run_macos`/`launch_mac_app`; screenshots/recording → `screenshot`, `record_sim_video`; UI automation → `tap`, `swipe`, `drag`, `long_press`, `button`, `gesture`, `key_press`; project discovery → `discover_projs`, `doctor`, `manage-workflows`, plus `debug_*` LLDB tools. **`describe_ui` was not found** — UI-automation descriptions reference "the latest `snapshot_ui` or `wait_for_ui` output" instead. Tool-count figures conflict across sources: the docs tools reference says "All 82 tools MobileBuildMCP advertises" (v2.7.1), a homepage CLI sample shows 59, a third-party listing said 71 — treat 82 as documented, not authoritative, since the page was truncated before the full inventory.

### Apple's own MCP server: `xcrun mcpbridge` exists

Apple's "Giving external agents access to Xcode" doc instructs: Xcode → Settings → Intelligence → Model Context Protocol → turn on **"Allow external agents to use Xcode tools"**, then `claude mcp add --transport stdio xcode -- xcrun mcpbridge` (Codex: `codex mcp add xcode -- xcrun mcpbridge`), verified with `claude mcp list`, project open in Xcode. The page states no minimum Xcode version.

The binary is real and version-tracked: a repo of captured `tools/list` responses covers **26.3 (17C529) through 27.0 RC (27A266a), 27.1 RC and 27.2 RC (27B48)** — so it ships in both Xcode 26 and 27. Captured Apple tool names include `BuildProject`, `RunAllTests`, `GetTestList`, `RenderPreview`, `InvokeDebuggerCommand`, `DocumentationSearch`, `GetBuildLog`, `GetConsoleOutput`, the `DeviceInteraction*` family (install/run, synthesize, sessions), `AddEntitlement`/`AddInfoPlist`, and crash/performance report tools — build, test, **SwiftUI preview rendering**, LLDB, doc search, device interaction; no file read/write tool appeared in the portion read. Cursor's docs independently describe "Xcode 26.3+ exposes a built-in MCP server… through `xcrun mcpbridge`". MobileBuildMCP's own site says it "integrates natively with Xcode 26.3's Claude and Codex coding agents" and **proxies Xcode's own MCP tools**, so one server config can cover both.

## 2. Verification stack

**Simulator screenshots (verified).** `xcrun simctl io <device> screenshot <path>` with `--type=png|jpeg` (default png) and `--mask {ignored|alpha|black}` (`alpha` is screenshot-only, silently falling back to `black` for video). `recordVideo` finalizes only on SIGINT and refuses to overwrite. Headless is fine: `open -a Simulator` is "optional; headless works without it". The classic flake is racing a booting device — `simctl boot` returns immediately, so block on `xcrun simctl bootstatus <udid> -b` or you get blank/duplicated screenshots. One community reference reports `simctl status_bar override` no longer works on iOS 26+ (single source, unconfirmed).

**swift-snapshot-testing (verified).** Actively released: **1.19.7, published 2026-10-21**, not archived, ~4.4k stars, MIT. It **supports Swift Testing directly** — the README's primary example is `import Testing` with `@MainActor struct … { @Test func … { assertSnapshot(of: vc, as: .image) } }`, plus a `@Suite(.snapshots(record: .failed))` trait and `withSnapshotTesting(record:)`; XCTest still works via an `invokeTest()` override. Strategies are device-agnostic from one simulator (`.image`, `.recursiveDescription`, `.image(on: .iPhoneSe)`, `.iPadMini(.portrait)`) but "must be compared using the exact same simulator that originally took the reference" — pin the runtime in CI. README examples are UIKit/CALayer and claim "iOS, Linux, macOS, and tvOS" but never name an AppKit/NSView strategy: **macOS snapshot support is not explicitly documented**.

**Previews.** The documented community routes are plugin-based: **Prefire** generates snapshot tests via Swift Package plugins "using SwiftUI `Preview`", and **PreviewSnapshots** (doordash-oss/swiftui-preview-snapshots) shares `View` configurations between Previews and snapshot tests. Apple's own `RenderPreview` MCP tool is the other current lever for rendering a preview without a GUI. A first-class `#Preview`-as-test Xcode 26/27 API is **not verified**.

**Physical iPhone screenshots (verified negative for devicectl).** Recorded `xcrun devicectl` 518.27 (Xcode 26.4.1) help output lists copy/info/install/notification/orientation/process/reboot/sysdiagnose/uninstall — "None of them captures a screenshot, sends input, or returns a UI tree." Xcode 27's release note that agents "can now boot simulators, install and launch apps, synthesize touch events, and capture screenshots" is simulator-scoped, and its devicectl notes add only JSON-to-stdout and flag fixes. Working CLI routes: **pymobiledevice3 `developer core-device screen-capture screenshot`** (PNG via the core-device screencapture service, also `developer dvt screenshot`), **WebDriverAgent `GET /screenshot`** (base64 PNG), **idb** via lockdown `screenshotr` — all needing Developer Mode and a mounted developer DDI. A secondary blog claims `xcrun devicectl device capture -d <udid>` exists from "Xcode 26.6 or later"; this **conflicts** with the recorded 26.4.1 help output and is unconfirmed.

**Headless XCUITest on CI.** `xcodebuild test` is documented with `-scheme`, `-only-testing <target>/<suite-or-function>`, `-test-repetitions`, `-test-iterations`, `-run-tests-until-failure`, emitting an `.xcresult` bundle; one runner covers both Swift Testing (`@Test`, `@Suite`, tags) and XCTest. Runner-image-level constraints are in §4. The specific "headless XCUITest caveats" beyond the runner limitations are **not verified**.

**WidgetKit / Live Activities / ControlWidget in simulator** — **not verified**; no source was read on previewing or testing widget extensions, Live Activity `ActivityView`, or `ControlWidget` in the simulator.

## 3. Project tooling

**XcodeGen vs Tuist.** XcodeGen (`yonaskolb/XcodeGen`) is not archived: 8,897 stars, last push 2026-10-13, latest release **2.46.0 (2026-07-16)** with 13 commits since, plus 404 open issues. 2.46.0 added Swift-package `traits` (remote and local), preserved target declaration order, changed static-framework embedding, and bumped XcodeProj to 9.14.0 — **no mention of Xcode 27, iOS 26/27 SDKs or Swift 6 language mode** (absence is not evidence of absence). No "maintenance mode" statement appears on the release page; that claim circulates only in blog posts. Tuist (`tuist/tuist`, "Your platform team, as a service") is active (last push 2026-10-27) but is now a **monorepo**: its release feed interleaves CLI, server, runner and image tags, so GitHub's "latest release" resolves to `runners-controller@0.51.4`, and the newest visible CLI entry is `4.216.0-canary.4` (pre-release) — **the current stable CLI version is unconfirmed**. `brew install xcodegen`, `tuist generate` and mise invocation paths were not verified.

**Formatters/linters.** `swift-format` (`swiftlang/swift-format`) **604.0.0 (2026-09-16)**, repo active to 2026-10-26; SwiftLint (`realm/SwiftLint`) **0.65.1 (2026-08-21)**, pushed 2026-10-16; SwiftFormat (`nicklockwood/SwiftFormat`) **0.64.4 (2026-10-27)**. All three are shipping; they are not substitutes (formatting vs linting). `.swift-format` config keys, `swift format --in-place --recursive`, and whether it ships inside the Xcode 26/27 toolchain are **not verified**.

**Swift 6.2/6.3/6.4 and strict concurrency.** Swift **6.2** shipped main-actor-by-default isolation (its sample is labelled `// In '-default-isolation MainActor' mode`), `nonisolated` async functions running in the caller's execution context via an upcoming feature, and the `@concurrent` attribute. **SE-0466 "Control default actor isolation inference"** (Borla/Gregor) is Status "Implemented (Swift 6.2)" and adds a compiler setting to infer `@MainActor` isolation by default per module, under the approachable-data-race-safety vision. **Swift 6.3 exists — released 2026-03-24** (highlights: `@c`/`@implementation` C interop, module selectors, `@specialize`/`@inline(always)`, Swift Build preview, official Android SDK; no concurrency-default change claimed). **Swift 6.4 followed on 2026-09-15** — Swift Build default in SwiftPM, Subprocess 1.0, `@diagnose` (SE-0522), module selectors (SE-0491) — so 6.4, not 6.3, is the newest release. The exact Xcode build-setting name (`defaultIsolation`), plus `InferIsolatedConformances`, `NonisolatedNonsendingByDefault`, `nonisolated(nonsending)` and SE-0461, **could not be confirmed from primary sources** — do not rely on those spellings yet.

## 4. GitHub Actions hosted macOS runners

`macos-26` went **GA 2026-02-26**. The arm64 image (20261013.0424.1, macOS 26.6.2) and the Intel image (20260824.0517.1) both pre-install **Xcode 26.0.1, 26.1.1, 26.2, 26.3, 26.4.1, 26.5, and 26.6 (default)** under `/Applications/Xcode_<ver>.app` with `/Applications/Xcode.app` symlinked to the default — **no Xcode 27**. Xcode 27 lives on a separate preview label, `runs-on: xcode-27` (or `xcode-27-xlarge`), whose image runs **macOS 27.0.1 (26A434)** with Xcode 27.1 default plus 27.0 and 27.2 RC and iOS 27.0/27.1/27.2 SDKs. The repo policy is explicit: only one Xcode major per macOS version, and only three platform/minor SDK generations — so **you cannot get Xcode 27 on `macos-26`**, and older runtimes (e.g. iOS 18) are not provisioned on `macos-26` (installed simulator devices are iOS 26.2, 26.4, 26.5 only). Labels: arm64 `macos-latest`, `macos-26`, `macos-26-xlarge`, `macos-15`, `xcode-27`; Intel `macos-26-intel`, `macos-26-large`, `macos-15-intel`, `macos-15-large`; `macos-14*` deprecated. Headless-UI-test limitations: **arm64 runners have no static UDID** (Intel ones do, `4203018E-580F-C1B5-9525-B745CECA79EB`), no nested virtualisation, some community actions are not arm64-compatible, and preview/beta images are excluded from the SLA. Xcode selection is via versioned app paths and the `Xcode.app` symlink; an explicit `xcode-select -s` / `DEVELOPER_DIR` recommendation from a GitHub doc was **not** confirmed. Billing: standard hosted runners are "free and unlimited on public repositories"; per-minute macOS `actions_macos` rate is **$0.062** (3- or 4-core), roughly 10× Linux 2-core $0.006, and larger runners are always charged even for public repos. A lower-confidence billing page lists included private minutes of 2,000 (Free) and 3,000 (Pro); plan-quota figures beyond that were not confirmed.

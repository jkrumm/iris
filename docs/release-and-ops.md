# Release and operations reference

Deploy poller, release hooks, versions, Mac releases, TestFlight crash intake, secrets and downstream env of the mini deployment. Rules to follow: `scripts/AGENTS.md`.

`project.yaml` is the factory manifest (`deploy.mode make`, target `mini`, verify `make verify`, ship by push). `make version` prints the sha in
`~/.iris/deployed-sha` (read-only, one line), which the factory compares with a shipped commit after its hold.

Push to master deploys. LaunchAgent `com.jkrumm.iris` (KeepAlive, `ExitTimeOut` 60 s) runs
`scripts/launch.sh` from the deploy clone `~/.iris/app`, never this checkout; data lives in
`~/.iris/data`; it listens on `127.0.0.1:7730`. Doors: `iris.test` (local) and
`iris.mini.<domain>` (tailnet), both Caddy in `dotfiles/config/Caddyfile`.

- `com.jkrumm.iris-deploy` polls `scripts/mini-deploy.sh` every 120 s through `jobrun`. It deploys
  `origin/master` only when the `check` job is green on that SHA and no memo is mid-step
  (`/health` `inflight` is 0). It restarts only for runtime paths (docs, tests, Makefile and
  `launchd/` do not; `launchd/` prints a warning), and writes `~/.iris/deployed-sha` once the new
  pid answers `/health`. `make deploy` runs one tick now.

- First install or a changed `launchd/` template: `make mini-setup` / `make launchd-install` on the mini.

- **TestFlight crash intake** (`com.jkrumm.iris-testflight-crashes`, hourly through `jobrun`, `launchd/com.jkrumm.iris-testflight-crashes.plist.template`, log `~/Library/Logs/iris-testflight-crashes.log`): `scripts/testflight-crashes.ts` lists the `betaFeedbackCrashSubmissions` of `com.jkrumm.iris` over the App Store Connect API (Team key from `op://mini/apple-developer/asc-*` through `secrets-run`, ES256 JWT in memory, nothing in argv or logs), reads each new report's symbolicated `logText`, groups the new reports by exception type + top app frame (a frame that is only `<deduplicated_symbol>` stands alone) and files **one factory Issue per group** with `factory issue new --repo iris --title <title> --facts - --key testflight-crash-<oldest submission id of the group> --alone` (the owner path of the factory CLI, which authenticates itself on the mini; the facts JSON goes on stdin; `--key` is the factory's idempotency key, so the script does no `factory issue list` de-duplication of its own; `--alone` keeps a crash Issue from being chained behind open ones; facts: build, date, the owner's comment, exception type, the crashed thread's app frames, the log path). Seen submission ids and the Issue key per signature (exception + top app frame + build) live in `~/.iris/testflight-crashes-seen.json`: a later report of an already filed crash reuses its key (the factory answers with the stored Issue), a new build of the same crash is a new Issue; a lost file re-files the same groups under the same keys, which the factory treats as no-ops. Raw logs are written 0600 to the gitignored `.artifacts/testflight-crashes/` of the deploy clone (`~/.iris/app`); the tester's email and device facts are never copied. Each ASC request retries 5xx, 429, a 404 of a path that must exist and network errors 4 times (2, 4, 8 s): Apple answers 500s and stray 404s on a healthy key for hours. After the retries an API or `factory` failure exits 1 (`jobs-grade` reports it; a group that failed stays unseen and is retried next hour). `make testflight-crashes [ARGS=--dry-run]` runs one tick now (`--dry-run` prints the exact `factory issue new` command and the facts it would pipe in, files and writes nothing); **`make testflight-crashes-baseline` once after the first install** marks the reports that exist as seen without filing (the three of 2026-11-06 are build 702, fixed in 705/708, Issue 211). Tests: `scripts/testflight-crashes.test.ts` (fake ASC server, signature-verified JWT).

- Secrets: `.env.local.tpl` + `.env.mini.tpl` (+ optional `.env.mini.otel.tpl`) via `secrets-run`.
  `launch.sh` refuses to start if a base ref does not resolve; a missing OTel overlay starts degraded.
  Device tokens and the OTLP endpoint live in `op://mini/iris/*` (listed in
  `dotfiles-private/headless.refs`). Rotate a token: edit the field, `make secrets-seed` from the
  MacBook, `make launchd-restart`. The audio door is not a secret ref: `AUDIO_DOOR_URL` is a plain value in `.env.local.tpl`
  (`http://127.0.0.1:7792/v1`) and `launch.sh` reads the `iris=<token>` line of `~/.agent-workflows/data/door-tokens` (0600, local, owned by
  agent-workflows) into `AUDIO_DOOR_TOKEN` without echoing it; a missing file or line starts degraded (`transcribe`, `speech`) and says why on stderr.
  Rotate it by editing that file and restarting both LaunchAgents. `APNS_*` comes from the team-wide `op://mini/apple-developer/*` item (in `.env.mini.tpl`, seeded via `headless.refs`; `APNS_TOPIC` is the bundle id), so the APNs notifier runs; the `.p8` field holds the PEM on one line and `normalizePem` (`notify/select.ts`) rebuilds it.

- **Versions** (`scripts/version.ts`, tests `scripts/version.test.ts`): both apps get `0.MINOR.PATCH` computed from git at build time, deterministic for a commit, no tag and no stored state, so the `testflight` and `mac` hooks building the same SHA agree. The commits that count are the non-merge commits reachable from the SHA, not from the baseline (`BASELINE` in the script = the commit of `mac-v0.1.0-799`), that touch `apple/` (`--full-history`, so a merged PR's own commits count). `MINOR` = 1 + how many of them have a `feat` subject (any scope, `!` allowed); `PATCH` = how many are newer than the newest `feat` (all while there is none). A `feat` that does not touch `apple/` changes nothing. Both release scripts pass it as `MARKETING_VERSION` and read the archive's Info.plists back; a local build without the script is `0.0.0` (`apple/project.yml`). The Mac tag is `mac-v<version>-<build>`. A shallow clone cannot compute it (the script fails loud). `make testflight` and `make mac-release` take `DRY_RUN=1` to print version, build/tag and release notes without signing. TestFlight's "What to Test" is not filled (the build is processed minutes after the upload, which the script does not wait for).

- **Release hooks** (Wave 22): after a deployed tick, and on every tick whose SHA is already deployed, the poller runs `scripts/release-hooks.sh <sha>` (executed, not sourced; `release_hooks` in `mini-deploy.sh` is the only poller code). It starts, per hook, a **detached** job (own session, `jobrun com.jkrumm.iris-release-<hook> --lock iris-release-<hook> --timeout 4800`, output `~/Library/Logs/iris-release-<hook>.log`) that checks the exact SHA out into `~/.iris/release-src/<hook>` (a worktree: the poller's `git reset --hard` never moves sources under an archive) and runs the make target as `scripts/apple-slot nice -n 10 timeout 2400` (`APPLE_LOCK_WAIT` 1800; `FACTORY_SLOT_RUN_MS` 2700000, because factory kills a slot command after 30 min and answers rc 124, which once failed a 33 min Mac archive on a loaded host). The poller itself stays fast.
  Hooks: `testflight` (`make testflight UPLOAD=1`, marker `~/.iris/testflight-sha`) and `mac` (`make mac-release IDENTITY=developer-id`: the script refuses a bare call; marker `~/.iris/mac-release-sha`, skipped while the Makefile has no such target). Each is **off** unless the untracked `~/.iris/release.env` has `TESTFLIGHT=1` / `MAC_RELEASE=1` (read line by line, never sourced; absent = off, logged as `skipped` every tick). A hook is **due** when `apple/**` changed since its marker's SHA, when there is no usable marker, or, for `testflight` only, when the marker is older than 7 days (TestFlight builds expire after 90 days; a Mac release has no expiry and its tag, the commit count, would already exist). A due hook **starts only through the gate** (Issue 289): the marker (last success) is at least 12 h old, the Apple lock is free (`lockf -t 0`) and a factory test slot is free (`factory slot run` with a 1 ms wait, exit 75 = busy; no `factory` or a server outage counts as free), at any hour, so a release never runs next to another release or a lead's check; otherwise the tick logs `<hook> due (...) but waiting: <why>`. So a day of `apple/**` commits starts at most one automatic release per hook, and no single commit starts one. `make testflight` / `make mac-release` by hand never pass the gate. Tests override the gate with `RELEASE_MIN_INTERVAL_SECS`, `APPLE_LOCK`, `FACTORY_BIN` (a stub for `factory`). Every release build is capped at `-jobs ` (default 2, the Makefile's `XCB`, `testflight.sh`, `mac-release.sh` and `apple-proof` share the number; the log shows `xcodebuild -jobs N`), and the detached job samples its process tree's resident memory every 5 s: the peak is logged (`peak memory N MB`) and merged into the job state as `peak_rss_mb` + `peak_rss_run_id` in `~/.local/state/jobs/com.jkrumm.iris-release-<hook>.json` (the wrapper does it after `jobrun` ends, which rewrites the state; RSS counts shared pages per process, so it is an upper bound). Tests: `scripts/release-hooks.test.ts`. The marker is written only after the make target succeeded; a failure writes `~/.iris/<hook>-failed` and holds that hook off for an hour. `DRY_RUN=1 scripts/release-hooks.sh <sha>` prints what would start and changes nothing (`RELEASE_HOME` / `APP_DIR` override the paths). The App Store Connect record is `Iris Agents` (`com.jkrumm.iris`, iOS only, never listed: internal TestFlight only; the Mac app ships outside the store) with the internal group `Internal` (automatic distribution of every build, the owner as tester); both were created over the Team key's API (`POST /v1/betaGroups`, `POST /v1/betaTesters`), only the app record needs the web UI (`POST /v1/apps` is 403). The mini's `~/.iris/release.env` has `TESTFLIGHT=1`. The iOS target needs `apple/Iris/Assets.xcassets/AppIcon` (a single 1024 px opaque icon, `ASSETCATALOG_COMPILER_APPICON_NAME`) and the three Info.plists take `CFBundleVersion` / `CFBundleShortVersionString` from `$(CURRENT_PROJECT_VERSION)` / `$(MARKETING_VERSION)` (set in `apple/project.yml`): App Store Connect rejects an export without the icon or with a build number that differs from the archive's.

- **Mac releases** (Wave 22 M2, TDD §5 "Updates"): `IrisMac` is **not sandboxed** (entitlements: Hardened Runtime `audio-input` only; no App Group, no network entitlement) and updates itself with Sparkle 2.10.x (SPM, `Updater` over `UpdateEngine`; `SparkleUpdateEngine` only on a real launch, `IrisMacApp` passes it, so `-IrisFakeData`, snapshots and tests have no updater). `SUFeedURL` is `https://github.com/jkrumm/iris/releases/latest/download/appcast.xml`, `SUPublicEDKey` the public half of the key from `generate_keys` (private key in the mini's login keychain; the file backup `~/.local/state/apple-developer/sparkle-ed25519.key` goes to 1Password). `make mac-release` → `scripts/mac-release.sh`: archive with `MARKETING_VERSION=$(bun scripts/version.ts)` (see Versions) and `CURRENT_PROJECT_VERSION=$(git rev-list --count HEAD)` (the build number Sparkle compares; the app and every extension are read back for the version), sign (`development` = Apple Development of the paid team, never notarized, draft only; `developer-id` = Developer ID + `notarytool` + staple, needs the certificate in the keychain), `ditto` zip, `generate_appcast --embed-release-notes` (the `IrisMac-<version>-<build>.html` next to the zip is the item's description, what Sparkle's update dialog shows), verify the appcast signature with `sign_update --verify`, `gh release create mac-v<version>-<build>` with the zip and `appcast.xml` and the same notes as its body. The notes are the subjects of the `apple/` commits since the previous published Mac release's target commit (`scripts/version.ts notes`). A draft is never `releases/latest`; only Mac releases may be published on this repo (`latest` is the feed). **`sign_update` and `generate_appcast` read the key from `--ed-key-file`, not the keychain**: run headless they hang on the keychain's access prompt (verified). Moving to non-sandboxed moved the app's data from the container to `~/Library/Application Support/Iris`, and the Keychain item of the old (sandboxed) signature may not be readable (unverified: a prompt or a re-entered connection); check on first launch. Developer ID signing, notarization, stapling and Gatekeeper (`source=Notarized Developer ID`) are proven on the mini and on the MacBook; first published release `mac-v0.1.0-693` (2026-11-06), then `-694`. Sparkle 693 → 694 works on an install **without** quarantine (staged while the app runs, installed by `Autoupdate` right after a quit, no admin prompt, no quarantine on the result); a copy that keeps `com.apple.quarantine` (a browser-downloaded zip) runs from an `AppTranslocation` path and the silent update never starts (`docs/spikes/device-checklist.md` R3b): clear the flag after the install (`xattr -d com.apple.quarantine <app>` from Terminal) until the release ships as a DMG or the interactive alert is shown to work. The Sparkle private key and the Developer ID key + certificate are backed up as Documents `iris-sparkle-ed25519-private-key` and `iris-developer-id-key-and-cert` in 1Password vault `mini`; the key file on the mini stays because `scripts/mac-release.sh` (and the poller's `mac` hook) reads `SPARKLE_KEY_FILE` at run time: removing it needs the script to fetch the key through `secrets-run` first. Sparkle's helpers ship ad-hoc signed: the script re-signs them inside out before notarizing. The poller's `mac` hook is on (`MAC_RELEASE=1`) and made `mac-v0.1.0-697` itself (2026-11-06, notarized, `appcast.xml` verified); the poller's LaunchAgent PATH has no `/usr/sbin`, so build 737 (2026-11-08) archived, signed and notarized and then died at `spctl: command not found`; `release-hooks.sh` now puts `/usr/sbin:/sbin` on the job's PATH and `mac-release.sh` calls `/usr/sbin/spctl`. Between then and 2026-11-10 every tick logged `starting detached` and no job ever ran: the poller's `jobrun` SIGKILLs the script's process group the instant the script exits, and the bare `perl setsid ... &` child had not called `setsid` yet. `start_detached` now forks, `setsid`s in the child and hands a byte to the waiting parent before the script goes on, then the tick waits up to `START_CONFIRM_SECS` (10) for the job's first log line (`detached job started (pid, token)` in `~/Library/Logs/iris-release-<hook>.log`) and logs `detached job started (confirmed in its log)` or `NOT started` / `NOT confirmed` with the reason. A slow notary queue ends the run with `RESUME_BUILD=<n> RESUME_NOTARY_ID=<id>` to continue without a rebuild.
